# Create a project with the toolkit

For an existing application, use [prompt 12](12-existing-project-setup.md): it adopts or updates the applicable set without generating another foundation.

## Shortcut

Paste into the agent with access to the target directory:

```text
Read https://raw.githubusercontent.com/soumatheusgomes/vibe-coding-toolkit/main/docs/prompts/11-next-project-bootstrap.md and execute the setup in this directory.
Project: [name, problem, audience, main flows and constraints].
```

If you have the toolkit open, use the local file and create the application outside it. Publishing the recipe does not automatically publish generated projects.

## Prompt

```text
Prepare the foundation of a new project using the Vibe Coding Toolkit:
https://github.com/soumatheusgomes/vibe-coding-toolkit

Use the project description supplied with this prompt. The destination is the directory indicated by the user or the current project directory. If the current directory is the toolkit itself, create a sibling folder named after the project. Preserve existing files and changes.

1. If the toolkit is unavailable locally, obtain a copy in a temporary directory outside the application and record the revision used. Read docs/04-project-bootstrap.md, docs/06-project-defaults.md, docs/tools/README.md, docs/tools/16-vercel-skills.md and templates/README.md, plus applicable capability guides. Follow templates/project-docs/manifest.json for documentation. Use files from the same revision; do not mix versions or copy the entire repository into the application.
2. Inspect the client, instructions, files, runtime, package manager and available tools. Reuse global installations; configure everything with supported local scope in the project. Do not change global permissions, providers or preferences during this setup.
3. Generate PRODUCT.md from templates/product.md.template. Record the problem, audience, MVP, flows, requirements, constraints, assumptions and acceptance criteria. Use reversible assumptions for missing details; mark indispensable external decisions as pending. Do not invent features, integrations or credentials.
4. Generate the foundation using the stable version of create-next-app, with App Router, TypeScript, Tailwind, ESLint, src/ and the @/* alias. Consult APIs/setup through Context7 and current official sources; check flags, stable channels and peer dependencies. Review defaults against the product/runtime/host and apply compatible improvements within the authorized scope, recording the reason, source and date. Do not copy prereleases from examples without evaluating the channel. Preserve the existing package manager; prefer pnpm for a new project if available. In a nonempty destination, use a temporary scaffold and incorporate it without overwriting files. Do not regenerate an existing Next application.
5. Install the default core according to the guide: Drizzle ORM + PostgreSQL/pg for new persistence, Zod, server-only, Pino, clsx/tailwind-merge and Vitest. Copy/adapt templates/next/, preserving .env.example; align @types/node with the runtime and peers, and @next/env with Next. Keep the pool bounded, reusable and lazy; initial builds/tests must work without credentials. Do not invent tables; generate/review SQL and apply migrations only to an authorized destination. Preserve the existing database/ORM; omit persistence only when the product does not need it, with justification. Authentication, services and additional libraries depend on the product.
6. Install web skills from vercel-labs/agent-skills and find-skills from vercel-labs/skills locally, following the catalog and current upstream. Adjust removed/renamed names and relevant new skills; do not treat the list as permanent. Use frontmatter names, check --list and select the agents in use. Include all web skills in the catalog, even those intended for later use; installing a skill does not execute its actions. React Native/Expo applies only if the product targets that platform. Version local skills and skills-lock.json; avoid global/local duplicates with the same name.
   Evaluate every capability in the scope matrix: next-dev-loop and next-bundle-optimizer for compatible Next.js; supabase-postgres-best-practices for PostgreSQL with any provider; gh-fix-ci for supported Codex/GitHub Actions work; differential-review for security-sensitive changes; shadcn for an adopted/selected UI system; Sentry MCP for a chosen service and authorized organization/project; Harness2-inspired measured harness improvement as a default setup workflow. Follow docs/tools/23-harness2.md and prompt 15 without a separate component selection: establish the native method adaptation, run relevant initial harness smoke cases, preserve current client/model/authentication/permissions, and record the mode and reusable invocation in docs/setup.md and docs/quality.md. Only an observed failure justifies a candidate comparison; otherwise preserve working instructions. Reuse applicable evidence on unchanged setup reruns; material changes require relevant checks again. Keep any selected official CLI lab outside the application; benchmark dependencies, API billing, the bridge, and isolated execution need explicit authorization. Do not install it as an application dependency or restart optimization on setup reruns. Install applicable project skills, record other decisions with reasons, and follow each guide. Check Next.js/Turbopack, agent-browser and analyzer requirements without silently changing the stack or installing global prerequisites. Configuration, discovery and live validation are separate states. Missing accounts or tools block only dependent capabilities; do not invent a successful query, create a service or add an SDK by default.
7. Generate/fill in the nine manifest documents: README.md, PRODUCT.md, AGENTS.md and CLAUDE.md at the root; docs/architecture.md, docs/design.md, docs/onboarding.md, docs/quality.md and docs/setup.md. Use product/code facts, without placeholders, duplication or claims of checks that never ran. Safely consolidate an old product.md into PRODUCT.md on case-insensitive filesystems. Preserve Next-generated instructions and their version-matched documentation pointers. Establish native memory or a short index into canonical docs; record its location/loading mechanism, provenance/freshness rules, and clean-context retrieval check. Reuse the task handoff template only for unfinished multi-session work. CLAUDE.md imports AGENTS.md in one line. For other clients, use the documented format; do not copy Claude settings into Codex or vice versa.
8. Check Ponytail full, Caveman, Superpowers, RTK, Context7 and Graphify. Reuse working client plugins/hooks. If a component is missing, record the outstanding issue and configure the officially supported local alternative when possible. Prefer project scope for missing plugins when the client officially supports it; reuse a working global integration. Do not automatically reinstall global binaries or copy personal caches.
9. Apply templates/eslint/next-app.config.mjs.example and copy the entire eslint-rules/ folder (including next-base.mjs) and self-check. Enable official presets, the 350-line ceiling, logger, data boundary and Drizzle guards. For partial adoption/without persistence, use the appropriate lightweight profile without installing an ORM just for lint. For the new TypeScript foundation, copy the focused typed profile and measure its cost; use no-floating-promises/no-misused-promises as errors unless a documented compatibility/resource constraint requires a follow-up. Configure lint, lint:typed, typecheck (next typegen then tsc for supported versions), lint:rules, test, test:watch, build, check and, when there is a database, db:generate/db:migrate. Do not connect or migrate during check/build.
10. Configure local Context7 only if no active connection exists, reconciling existing files without secrets. Copy and adapt Graphify exclusions; generate the initial graph with code extraction and no external LLM when the CLI supports it. Do not install Git hooks or refresh automations.
11. Make security review reusable: copy only the self-contained Prompt block from docs/prompts/13-security-review.md into the existing project prompt location when appropriate, adapting paths while preserving its limits, or record its versioned source/invocation in docs/quality.md; keep the source revision and update method. It supports read-only repository and diff reviews with private reports and manual fallback when the optional skill is unavailable. Run relevant disposable harness cases from docs/07-harness-evaluation.md, distinguishing observed behavior from unavailable host interactions. Run checks and dependency audits, distinguishing production from development and recording advisories with no available fix. Do not force downgrades or claim absolute security. Validate boundary tests and SQL generation without credentials; distinguish mocks, an embedded SQL engine and a real connection. Validate the application on a free port and record versions, revision, scopes, components and evidence in docs/setup.md. Check skill discovery and a real Context7 query when the host allows it; distinguish present files from tested integrations. Stop only processes and temporary resources created by setup. Adapt commands to the actual shell; on Windows use the skills CLI's --copy mode to avoid junctions with absolute paths.

This request authorizes bootstrap implementation and local validation. Present relevant decisions and proceed without further design/plan approvals. Ask questions only when indispensable information is missing to prevent data loss or incorrect implementation; continue independent steps. A pending external choice does not authorize inventing its outcome.

Ponytail full: the smallest complete solution. Caveman: concise conversation in the user's language without reducing clarity; normal wording in code, documentation and commits. Superpowers: process proportional to the scope and authorization already granted. Context7: current documentation, no secrets in queries. RTK: supported commands, no duplicate wrapper. Graphify/Caveman: preserve the native client, model and session authentication; do not silently change provider or enable API billing or a proxy. Pass the model explicitly if supported delegation is available.

Do not add push blockers on main, branch/worktree requirements, pre-commit/pre-push hooks or Git protections. Do not publish, push, purchase services, send messages or implement the entire product as a consequence of this bootstrap. Update the responsible document when behavior, commands, schema or decisions change; older recommendations may be revised with current evidence. Deliver the configured foundation, completed documentation, evidence, outstanding issues, the run command and the next MVP task.
```
